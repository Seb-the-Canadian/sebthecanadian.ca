## In one paragraph

The site is in good shape: axe-core finds no violations on ten of eleven
pages, every page fits a phone without sideways scrolling, text contrast
clears AA everywhere except one hover state, and the skip link, Tab order,
focus ring, theme button, `?` overlay and `g`-chords all work in Chromium.
The test that felt broken was in Safari, and in Safari the Tab key reaches
nothing on this site by default: Safari only tabs to text fields unless a
setting is on, and the site has none (K1). Inside the site the problems
are narrower: a hidden link that swallows focus on the home page, a shortcuts overlay that calls
itself modal but lets focus wander behind it, heading anchors that are
invisible when focused, and a theme button that cycles through three states
and tells screen readers nothing about which one it is in. Several of the
smaller items are one-line fixes.

## Keyboard navigation: what was actually found

Reproduced on the live site, keyboard only:

| Step | Result |
|------|--------|
| First Tab | "Skip to content" appears top-left with a green focus ring. Works |
| Enter on it, then Tab | Focus lands inside the page content, past the nav. Works |
| Tab through the nav | Home, Writing, Projects, About, then the theme button, each with a visible ring. Works |
| Enter / Space on the theme button | Switches theme and label. Works |
| Next Tab after the button (home page) | **Focus vanishes.** It is on a visually hidden link (`https://sebthecanadian.ca`, the h-card `u-url`) drawn at 1×1 px. Finding K2 |
| `?` | Overlay opens, focus moves inside. Works |
| Tab inside the overlay | **Focus leaves the overlay** and lands on the skip link behind the dimmed page. Finding K3 |
| Escape | Overlay closes, focus returns to where it was. Works |
| `g` then `p` | Goes to /projects/. Works |
| First Tab into About, Uses, Links content | Lands on a `#` heading anchor that is invisible until focused and then only half visible. Finding K4 |

So in Chromium the chords and the overlay do work. **The original test was
in Safari on a Mac, and that is the explanation.** The same pass, re-run in
the Safari engine (Playwright WebKit 27.2 on this Mac, where macOS
"Keyboard navigation" is off, as it is by default):

| Step | Result in the Safari engine |
|------|-----------------------------|
| Tab, Tab, Tab | **Focus stays on the page body.** Nothing is reached: not the skip link, not the nav, not the theme button |
| Option+Tab, four times | Skip to content, Home, Writing, Projects. Everything is reachable this way |
| `?` | Overlay opens with focus inside. Works |
| Escape | Overlay closes. Works |
| `g` then `p` | Goes to /projects/. Works |
| Every link and button given `tabindex="0"`, then plain Tab seven times | Skip to content, Home, Writing, Projects, About, the theme button, then the hidden h-card link (K2). Enter on the button switches the theme |

Why: by default Safari's Tab key visits text fields only. Links need
Safari → Settings → Advanced → "Press Tab to highlight each item on a web
page"; buttons need macOS System Settings → Keyboard → "Keyboard
navigation"; holding Option while pressing Tab reaches both without
changing anything. This site has no text fields, so Tab does nothing at
all, which is exactly "doesn't seem to work". The `?` overlay and the `g`
chords listen for keys on the page rather than on a focused element, so
they work in Safari as they are. Chrome reaches everything, and then hits
K2, K3 and K4, which are real defects either way.

Two ways to respond; it is open question 2 below:

- **Document it** (the convention). A short "On a Mac" note on
  `/keyboard/` and in the runbook. Every other site behaves the same way
  in Safari.
- **Work around it.** A few lines in `keyboard-nav.js` give every link and
  button an explicit `tabindex="0"` when the page loads. Safari treats that
  as "the author wants this in the Tab order", verified in the table above.
  No effect in Chrome, or in Safari with the setting on (Firefox not tested: it would not launch in this session). Costs:
  it overrides a Safari default rather than respecting it, and it needs
  JavaScript (without it, Safari behaves as today). The note on
  `/keyboard/` is worth having either way.

## Proposed design: two-state theme toggle

Plain words first. The button becomes a switch between Light and Dark only.
Until you press it, the site follows your computer's setting. The first
press flips you to the other one and remembers it, in this browser, until
you press again.

- **First visit:** no stored choice, so the page follows
  `prefers-color-scheme`. The switch shows the state you are currently in.
- **Press:** flips to the other theme, stores `light` or `dark` in
  `localStorage` (same key as today, `theme-preference`; an old stored
  `system` value is treated as "no choice").
- **No flash:** a tiny inline script in `<head>` reads the stored value and
  sets `data-theme` before the first paint; `theme-toggle.js` keeps only the
  button.
- **The button:** a real `<button type="button" role="switch">` with a
  fixed accessible name "Dark theme" and `aria-checked="true|false"`.
  Screen readers hear "Dark theme, switch, on" and "off". The visible text
  stays short: "Dark" with a moon or "Light" with a sun, or just the word.
  A visually hidden live region says "Dark theme on" / "Light theme on"
  after each press. (Alternative: a plain button named "Switch to dark
  theme" whose name changes on press. The switch is more honest about
  state.)
- **System colours follow:** `color-scheme` and the `theme-color` meta tag
  follow the chosen theme.
- **Without JavaScript:** no button, the site follows the system setting,
  as today.
- **Not included:** no "back to system" state. If you ever want it back,
  the natural place is a line in the colophon, not the button.

## Proposed design: shortcuts overlay as a dialog

`keyboard-nav.js` builds the overlay as a `<dialog>` and opens it with
`showModal()`. Focus moves to the dialog, Tab cycles inside it, Escape
closes it (the browser does this; the `?` toggle stays), and the page
behind is inert while it is open. A "Close" button is added at the bottom
for mouse and touch. Existing classes keep the look; a few lines of CSS
restyle the `::backdrop`. Focus returns to where it was on close, as now.
